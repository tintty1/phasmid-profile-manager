# Profile settings

A profile is one long-lived machine: a Phasmid profile describing the device,
the browser data directory Chrome writes, and a proxy. This page explains what a
person chooses, what is generated, and what a launch does with it. What Phasmid
does with a profile once the browser has it is described in the
[Phasmid README](https://github.com/tintty1/phasmid#readme) and
[`docs/architecture.md`](https://github.com/tintty1/phasmid/blob/main/docs/architecture.md).

## The machine

A profile's machine is a complete Phasmid profile JSON
([`profiles/schema.json`](https://github.com/tintty1/phasmid/blob/main/profiles/schema.json)
in the Phasmid repository): OS, hardware, display, GPU, canvas and audio,
fonts, locale, speech voices, media devices, codecs, WebAuthn, capabilities,
network and a seed for every deterministic perturbation.

It is generated by the installed release's own
[`tools/genprofile`](https://github.com/tintty1/phasmid/blob/main/tools/genprofile/README.md),
run in a child process from the release's source tree (`core/genprofile_driver.py`),
so a profile is always generated by the generator of the browser that will read
it. genprofile draws GPU, font, voice and codec values only from captured real
devices. The result is validated against the schema and stored on the profile as
`fingerprint`.

- The profile response carries a short **summary** of it as `fingerprint`: id,
  seed, OS and version, `navigator.platform`, cores, memory, screen, device
  pixel ratio, GPU renderer and `gpu_id`, font count, timezone, languages, the
  WebRTC public address, whether a position is set, the installed browser
  version, and the OS fields described [below](#when-the-os-setting-and-the-machine-disagree).
  Its keys may grow with Phasmid's schema.
- `GET /api/v1/profiles/{id}/machine` returns the whole JSON, as the next
  launch would hand it to the browser apart from a location move. It answers
  `404` while the profile has no machine yet. In the UI: **View machine JSON**
  in the profile's Machine panel.

The browser version is not part of the pin. Phasmid reports the version it was
built from, so every profile reports whichever release is installed, and
installing a newer release updates all of them at once, as on a real machine.

## Settings

`browser_settings` holds what a person chooses. genprofile does the rest.

| Field | Values | Effect |
| --- | --- | --- |
| `os` | `linux` (default), `windows` | The OS the machine claims. Used only when a machine is generated |
| `gpu` | `<vendor_id>:<device_id>`, e.g. `0x10de:0x2504`, or unset | The GPU the machine claims. Unset, genprofile draws one from the captures, weighted by how often each occurs. Used only when a machine is generated |
| `languages` | list, e.g. `["de-DE", "de", "en-US", "en"]`, or unset | Unset, derived from the exit address. Set, wins over it on the next launch |
| `timezone` | IANA name, e.g. `Europe/Berlin`, or unset | Unset, derived from the exit address. Set, wins over it on the next launch |
| `webrtc_policy` | `default`, `default_public_interface_only`, `default_public_and_private_interfaces`, `disable_non_proxied_udp` | Chrome's WebRTC IP handling policy, written into each launch's profile file. `default` is what stock Chrome does |

`GET /api/v1/fingerprints/gpus?os=windows` lists the GPUs a machine may claim:
those captured on a real host, and those the captured host class backs with the
same WebGL surface (genprofile's claims). Each entry has `os`, `gpu` (the value
for `browser_settings.gpu`), `renderer` (the WebGL renderer pages see) and
`weight`. The list is empty until the browser is installed.

## When a machine is generated

- **On create**, when the browser is installed and `generate_fingerprint` is
  true (the default). Without an installed browser the profile is created
  without a machine.
- **On the first launch** of a profile that has none: one created before the
  browser was installed, one imported from Excel, or one whose machine was
  dropped.
- **On clone**, unless `regenerate_fingerprint` is false. Two profiles sharing a
  machine report the same GPU, screen, cores and seeds, which makes them
  provably one computer.
- **On *Regenerate fingerprint*** (`POST /api/v1/profiles/{id}/reset-fingerprint`):
  a new seed, so new hardware. Without an installed browser the old machine is
  dropped and the next launch generates one. Refused for a protected profile.

A new machine gets a fresh 128-bit seed. A machine generated without a known
exit address (on create, for example) gets this computer's timezone until its
first launch moves it.

## What a launch does

1. **Find the exit address.** The manager asks, through the profile's proxy,
   what address the internet sees (`api.ipify.org`, then
   `checkip.amazonaws.com`, then `icanhazip.com`, over verified TLS, with an
   8-second timeout). Without a proxy that is this computer's public address. An answer
   that is not an IP address counts as a failure.
   - A proxied launch whose proxy does not answer is **refused**, so the browser
     never starts at a location the proxy does not have.
   - Without a proxy, a failed lookup is logged and the machine stays where it
     was.
2. **Pin or move the machine.** A profile without a machine gets one, placed at
   the exit. A profile with one is moved when its location no longer matches:
   - no timezone stated and the exit differs from the address the machine was
     last placed at;
   - a timezone stated that differs from the machine's, or the exit changed
     while a timezone is stated;
   - languages stated that differ from the machine's.

   Moving runs genprofile again with the **same seed**, OS and GPU, and takes
   only the location group from the result: the whole `locale` section
   (timezone, languages, Intl locale, geolocation) and
   `network.webrtc.public_ip`. Everything else is copied from the stored
   machine rather than trusted to regenerate identically, so a newer genprofile
   that samples differently never gives an existing profile new hardware.
3. **Write the session's files** into `<data dir>/run/<profile id>/`, mode 0700:
   `profile.json` (the machine plus the profile's `webrtc_policy`, mode 0600),
   `proxy-args` for an authenticated proxy (mode 0600), the browser's log and
   its pid. The directory is removed when the session ends.
4. **Start the browser** as a process of its own:

   ```
   chrome --phasmid-profile=<run dir>/profile.json
          --user-data-dir=<data dir>/profiles/profile_<id>
          --remote-debugging-port=0 --no-first-run --no-default-browser-check
          --password-store=basic
   ```

   plus `--disable-gpu` when no GPU device (`/dev/dri`, `/dev/nvidia0`) is
   present, as Phasmid's Docker image does; `--headless` for headless launches;
   `--ozone-platform=x11` on a virtual display; any `args` the launch request
   carries; and the proxy, below. `--password-store=basic` keeps cookies and
   saved passwords from being tied to this login's desktop keyring, so an
   exported profile, or one opened from Docker and from the desktop, keeps its
   sessions.
5. **Wait for CDP.** Chrome picks a free loopback port and writes it to
   `DevToolsActivePort` in the profile directory; the manager waits up to 45
   seconds for it. The launch response then carries `cdp_endpoint`.

The machine and `last_used` are written with a targeted update that does not
bump `row_version`, so a launch does not make an open edit form fail to save.

When the browser exits (the window closed, a crash, or `POST .../close`), the
session, its VNC display, its run directory and its lease are cleaned up. `close`
first asks the browser to close over CDP so it writes its session out, then
signals its process group.

## What follows the proxy

| Pinned: the hardware | Follows the exit address |
| --- | --- |
| `os`, `hardware`, `display`, `gpu` | `locale.timezone`, `locale.languages`, `locale.intl_locale` |
| `canvas`, `audio`, `fonts`, `speech` | `locale.geolocation` |
| `media_devices`, `media`, `webauthn`, `capabilities` | `network.webrtc.public_ip` |
| `system_colors`, `network.connection`, `automation`, `seed` | |

Phasmid's schema requires the WebRTC address to equal the exit address, and a
Berlin clock behind a Tokyo exit is a contradiction any page can measure. That
is why the location group is regenerated rather than pinned. genprofile derives
it from the exit address with DB-IP City Lite, timezonefinder and Unicode CLDR;
its README documents the rules (the city's zone, a position drawn around the
city with 25-100 km accuracy, Chrome's default accept-languages for the
country). If it
cannot place the exit (a private address, or one the database knows only by
country), generation fails and the launch is refused with `400` and genprofile's
message.

### Stating a timezone or languages

Leave both unset for nearly every profile.

- A **stated timezone** replaces the exit's location, not its address: the
  machine gets that zone, **no geolocation**, and `en-US, en` unless languages
  are stated too. The WebRTC address stays the exit's, because WebRTC's UDP does
  not go through the proxy and Phasmid answers the server-reflexive candidate
  with this address. *Check proxy* warns when the stated zone is on a different
  clock from the exit's. genprofile's README notes that a Windows profile with no
  position is a stronger tell than a Linux one, so prefer leaving the timezone
  unset on Windows profiles.
- **Stated languages** replace only the languages; the timezone and position
  still come from the exit.

### Clearing a stated timezone

*Clear timezone, follow the proxy* in the profile form, the **Clear timezone**
bulk action on a selection in the profiles list, and
`POST /api/v1/profiles/clear-geography` with `{"profile_ids": [...]}` unset the
stated timezone of each profile. Languages are left alone: an English browser is
unremarkable from any country, and changing them would change the profile's
identity. Nothing is cleared automatically. Setting or clearing a stated
timezone or language list forgets where the machine was placed, so the next
launch places it again, even behind the same exit.

## When the OS setting and the machine disagree

The machine is what a page sees, so changing `os` on a profile that already has
one changes nothing observable until a new machine is generated. That is
allowed, because it is often the first step towards regenerating. It is
reported: the summary carries `pinned_os`, `settings_os` and `os_mismatch`, the
server logs a warning on the save, and the Machine panel shows a banner with the
two ways out.

| | What it does | What it costs |
| --- | --- | --- |
| **Keep this machine** | Puts the OS setting back to what the machine reports | Nothing; no machine value changes |
| **New \<OS\> machine** | Generates a new machine for the OS setting | New seed, hardware, screen, GPU and fonts; a warmed-up account is on different hardware |

Neither is preselected. `POST /api/v1/profiles/{id}/reconcile-os` refuses when
the two already agree, when there is no machine, and, for a new machine, when
the browser is not installed or the profile is protected.

Changing `gpu` on a profile with a machine likewise has no effect until the
machine is regenerated; it is not reported as a mismatch.

## Proxies

`proxy_config` is `{type, server, username?, password?}`, with `type` one of
`http`, `https` or `socks5` and `server` as `host:port`. `socks4` is accepted
in the record but refused at launch and by the proxy check: the exit address a
launch places the machine at cannot be looked up through SOCKS4.

### How a proxy reaches the browser

Chrome ignores credentials in `--proxy-server` and would prompt for them. So
HTTP, HTTPS and SOCKS5 proxies go through Phasmid's
[`tools/proxyroute`](https://github.com/tintty1/phasmid/blob/main/tools/proxyroute/README.md)
with the profile's proxy as `--proxy-default`. proxyroute hands Chrome a PAC
script and, for a proxy with credentials, relays it through a loopback SOCKS5
listener that adds them. Its arguments, credentials included, are passed as
`@<run dir>/proxy-args`, so they never appear in `ps`. With credentials,
proxyroute stays as the browser's parent; the manager watches and signals the
whole process group.

### Checking a proxy

*Check proxy* in the profile form and in a profile's row menu reaches the
internet through the proxy, places the exit address with the same database and
rules genprofile uses, and reports the address, country, timezone and round
trip. It then lists what a page could notice:

| Reported as | When |
| --- | --- |
| Error | The profile cannot launch: a SOCKS4 proxy |
| Warning | A page can see a contradiction: a stated timezone on a different clock from the exit's, or a stored position more than 500 km from it |
| Note | Worth knowing: a stated zone with the same clock but another name, a position 100-500 km away, no timezone set (it follows the proxy), the machine last placed at another exit (the next launch moves it), or a working proxy whose address could not be placed |

The form checks what is on screen, so a proxy can be tested before the profile is
saved. A check of a saved profile keeps its answer on the profile, so the list
shows each proxy's last state; nothing polls.

## Windows profiles

A Windows profile on a Linux host reports Windows wherever the host allows it.
Text is measured and fonts resolve as on Windows only when Phasmid has a Windows
font store, which it does not ship: the font files are supplied by the user, and
Phasmid checks them against a manifest. By default Phasmid looks in
`$XDG_DATA_HOME/phasmid/fonts/windows/<os.build>`; `--phasmid-windows-fonts=<dir>`
names another directory. See the
[Phasmid README](https://github.com/tintty1/phasmid#quick-start) and
[`docs/surfaces.md`](https://github.com/tintty1/phasmid/blob/main/docs/surfaces.md).

The manager does not pass that switch. Put the store at Phasmid's default path
for the user the browser runs as, or pass the switch in a launch's `args`. In
Docker the default path is under the container user's home, which is not in the
`/data` volume: mount the store and pass the switch. Without a store, the browser
logs `Phasmid: host cannot back <field>` at startup and reports the claim as well
as it can ([unbacked claims](https://github.com/tintty1/phasmid/blob/main/docs/architecture.md#unbacked-claims)).
The same applies to a profile that claims Widevine (`--phasmid-widevine-cdm`).

## Moving a profile

`GET /api/v1/profiles/{id}/export` packs the profile record, its machine and its
browser data directory into one zip (`<name>.phasmid.zip`);
`POST /api/v1/profiles/import` restores it under a new id. In the UI:
*Export…* in a profile's row menu, and the import button in the toolbar.

- The browser must be closed. Exporting a running profile, or one leased by
  another instance, is refused with `409`.
- Chrome's disposable caches (HTTP, code, GPU and shader caches) are left out.
- **The archive is not encrypted.** It contains live session cookies, saved
  logins and the proxy password.
- The group is dropped (its id belongs to the source instance), and so is the
  last proxy check.

## Known limitations

- **Linux x64 hosts only.** Profiles may claim Linux or Windows; Phasmid does not
  support macOS profiles.
- **No SOCKS4.** The exit lookup uses httpx, which has no SOCKS4 support, so a
  SOCKS4 profile is refused at launch. Use SOCKS5, HTTP or HTTPS.
- **`window_size` on launch is ignored.** The window is the profile's own size,
  so the size a page measures is the size the machine claims.
- **Without a GPU device the GPU claim is not backed by hardware.** The browser
  runs with `--disable-gpu` and renders WebGL on SwiftShader; the browser's
  startup log names any claim the host cannot back.
- **Changing `os` or `gpu` does not change an existing machine.** Use
  *Regenerate fingerprint* or the reconcile banner.
